# AI Coding 模型/契约/测试驱动的 Agentic 开发

> **AI 时代不是“原型驱动开发”，也不是“提示词驱动开发”，而是“模型/契约/测试驱动的 Agentic 开发”。
> 谁能把上下文、接口、测试和验收体系做好，谁的 AI 编程质量才会真正拉开差距。**

## 1. AI Coding

你的感觉是对的：**如果只是“用自然语言描述需求，让 AI 写代码”，这已经不新了**。现在 Claude Code、Codex、Cursor、Trae、OpenHands、各类 Agent IDE 都已经在做类似事情。

大会上真正值得关注的，不是“AI 能写代码”，而是这几个问题：

**第一，AI 能不能理解一个已有大项目。**
不是新建一个 Todo App，而是进入一个十几万行、几十万行、上百万行的项目里，知道哪些地方能改，哪些地方不能改。

**第二，AI 能不能按企业规范生成代码。**
包括目录结构、命名、日志、异常、权限、审计、接口风格、数据库变更规范、前端组件规范。

**第三，AI 改完之后能不能自己验证。**
这就是你后面说的测试工程。AI 编程真正的瓶颈不是“生成”，而是“验证”。

**第四，AI 能不能在低 token 成本下持续工作。**
火山开源的 OpenViking 文档里也强调了 Agent 上下文管理的重要性：把 memory、resource、skill 等上下文以类似文件系统的方式组织，让 Agent 用更低成本找到需要的信息。这个方向比单纯“提示词写得好”更重要。([GitHub][2])

所以我会把 AI Coding 分成三代：

| 阶段                     | 特点                     | 问题                |
| ---------------------- | ---------------------- | ----------------- |
| 1. Copilot 式补全         | 补函数、补代码片段              | 对业务整体无感           |
| 2. Vibe Coding         | 自然语言生成页面/功能            | 容易 demo 化、工程质量不稳  |
| 3. Agentic Engineering | 读需求、改代码、跑测试、提交 PR、生成报告 | 核心难点在上下文、测试、权限和治理 |

你的判断应该是：**大会讲的是第 2 代到第 3 代之间，但如果没有讲测试、契约、上下文、工程治理，就只是包装。**

## 2. “原型驱动开发”你质疑得很准确

你说的“原型驱动式开发”，更准确应该叫 **高保真原型驱动开发**。传统做法是：

先把页面交互做得几乎和正式产品一样，用假数据展示；
业务、市场、前端都觉得 OK；
然后后端、数据库、真实业务逻辑再介入。

这个模式在传统时代有价值，因为它能快速统一认知。但它的问题也非常明显：

**一旦业务结构变了，原型越高保真，沉没成本越大。**
比如一开始页面上只是“客户信息”，后来发现要拆成客户、联系人、企业主体、合同主体、开票主体、权限主体，那整个页面、接口、数据结构都要重来。

所以你提出的反方向更接近正确答案：**不要先做漂亮原型，而是先做底层对象、数据关系、接口契约和可运行骨架。**

我建议把它叫成：

> **领域骨架驱动开发**
> 或者
> **契约优先 + 垂直切片开发**

这个比“原型驱动”更适合 AI 时代。

## 3. 更好的开发顺序：不是“原型先行”，而是“领域模型 + 可运行骨架先行”

我建议你把流程改成这样：

### 第一步：先定义业务对象和关系

比如你之前说学籍系统，应该先识别：

学生、班级、科目、教师、成绩、选课、学期、考试、学籍状态。

然后判断：

一对一、一对多、多对多、状态流转、生命周期、权限边界。

这一步不是数据库设计本身，而是**领域对象建模**。

---

### 第二步：定义接口契约

在 AI 编程里，这一步非常关键。

比如：

```text
POST /students
GET /students/{id}
POST /classes/{id}/students
GET /students/{id}/scores
```

每个接口要提前定义：

输入字段、输出字段、错误码、权限、幂等性、分页、排序、状态机限制。

这一步做好，AI 生成前端、后端、测试都会稳定很多。

---

### 第三步：生成最小可运行骨架

不是做漂亮 UI，而是做：

后端实体、表结构、接口、基础权限、基础页面、最小测试。

页面可以很丑，但必须跑通真实链路。

也就是：

> 数据库是真的，接口是真的，业务流是真的，UI 可以暂时粗糙。

这和你说的“先把骨架和 interface 做好，最后才做展示层”是一致的。

---

### 第四步：再做高保真 UI 和体验优化

到这一步，UI 调整才不会把底层业务结构推翻。

所以我建议你以后内部可以这样定原则：

> **原型可以早做，但不能让原型决定领域模型。
> UI 可以驱动体验讨论，但不能驱动底层结构设计。
> 真正的第一版，不是高保真页面，而是可运行的业务骨架。**

---

## 4. 测试工程才是 AI Coding 的真正胜负手

你后面讲得最关键。

现在 AI 编程最大问题不是“写不出代码”，而是：

写完之后你不知道它有没有破坏别的地方。

尤其是大项目里，AI 很容易：

改了一个公共函数，影响十几个模块；
改了一个类型定义，前端一堆页面潜在异常；
改了接口字段，后端测试过了但前端挂了；
Mock 很顺利，真实联调全失败；
页面能看，但边界状态、权限、异常流程错了。

所以我认为 AI 时代测试工程要从“测试用例”升级成：

> **变更感知测试系统**

也就是你说的：**90% 的修改能够感知影响范围，然后只跑局部测试，而不是每次全量回归。**

---

## 5. 怎么做到“局部测试”，而不是每次全量回归？

核心是建立四张图。

### 第一张：代码依赖图

知道 A 文件依赖 B，B 影响 C，C 被哪些服务调用。

比如：

```text
UserService.ts 修改
影响：
- UserController
- OrderService
- PermissionService
- user-profile 页面
- user-list 页面
- auth 中间件
```

---

### 第二张：接口契约图

知道某个 DTO、API、字段变化，会影响哪些调用方。

比如 `user.status` 从 string 改成 enum，就要知道哪些前端页面、哪些后端服务、哪些报表在使用。

---

### 第三张：测试映射图

知道每个测试用例覆盖哪些代码、接口、页面和业务场景。

这样 AI 改完代码后，可以自动判断：

这次只需要跑：

```text
UserService 单测
UserController contract test
权限相关集成测试
用户列表 Playwright 测试
```

而不是全量跑几千个测试。

---

### 第四张：业务场景图

比如：

开户、审批、报销、付款、发票识别、订单退款、客服投诉处理。

AI 改了一个字段，要能映射到业务场景：

```text
修改 invoice.amount
影响：
- 发票识别
- 报销单提交
- 财务审核
- 多币种金额转换
- 付款申请
```

这才是企业级测试工程。

---

## 6. Mock 不能乱用，要分层

你说得也对：现在一做 AI 或多模块联调，就会大量 Mock。Mock 太多会带来一个问题：

> Mock 全通过，真实环境全失败。

所以我建议分成四类：

| 类型                     | 适合场景              | 风险       |
| ---------------------- | ----------------- | -------- |
| Fake                   | 本地轻量替代真实服务        | 最推荐      |
| Stub                   | 固定返回值             | 适合单元测试   |
| Mock                   | 验证调用行为            | 容易过度耦合实现 |
| Testcontainer / 沙箱真实服务 | 数据库、Redis、MQ、对象存储 | 成本高但可信   |

比如数据库不要永远 Mock，最好用 Testcontainer 或测试库。
外部 AI 模型可以 Mock，但要保留一组真实调用的回归集。
OCR、多模态、LLM 这种不稳定模块，需要做 **Golden Dataset + 评估脚本**，而不是只看代码测试。

## 7. UI 测试不要重度依赖 Computer Use

你说“不要重度投屏依赖”，这个判断非常重要。

Computer Use / 浏览器视觉操作适合：

最后一公里验收；
复杂第三方网页自动化；
非结构化页面；
无法拿 DOM 的场景。

但它不适合作为日常高频回归测试，因为成本高、慢、不稳定、token 消耗大。

更好的顺序应该是：

```text
1. 纯函数单测
2. Service 单测
3. API contract test
4. 组件测试
5. Playwright DOM 测试
6. 少量视觉截图回归
7. 极少量 Computer Use 黑盒验收
```

也就是说，UI 自动化优先用 DOM locator，而不是让 AI “看屏幕”。

对于你之前说的 OA 自动填报、发票识别、拖拽上传那种场景，最好是：

AI 负责理解页面结构和生成操作策略；
Playwright/CDP 负责稳定执行；
Computer Use 只在 DOM 拿不到或页面极其复杂时兜底。

## 8. AI 编程的提示词：不能只讲故事，也不能只写技术规则

你最后这个问题非常关键：

视频生成里说“不要用专业镜头语言，要用讲故事的方式”；
那编程是不是也应该少写技术规则，多讲用户体验？

我的判断是：

> **视频生成可以更多讲故事，软件开发不能只讲故事。**

原因是两者目标不一样。

视频生成有很大的审美容错空间。
比如你说：“一个老人走在雨夜的街头，回忆年轻时的故乡。”
模型可以自由发挥镜头、光影、节奏、表情。

但软件开发没有这么大的自由度。
一个字段错了、权限错了、状态流转错了，系统就是错的。

所以编程提示词应该是四层结构：

```text
第一层：业务目标
第二层：用户体验
第三层：领域模型和接口约束
第四层：验收标准和测试要求
```

不能只写：

```text
帮我做一个好用的报销系统。
```

也不能只写：

```text
使用 Vue3 + SpringBoot + MySQL，实现 CRUD。
```

更好的写法是：

```text
我要做一个员工报销系统。

业务目标：
员工上传发票和水单，系统识别金额、日期、抬头、税号，并生成报销草稿。

核心对象：
Employee、Invoice、PaymentProof、ExpenseClaim、ApprovalTask。

状态流转：
草稿 -> 已提交 -> 部门审批 -> 财务审批 -> 已付款 / 已驳回。

接口要求：
提交报销单时必须校验发票金额合计等于申请金额。
发票重复上传时要提示重复，不允许重复报销。

用户体验：
员工只需要拖拽文件，系统自动生成草稿，用户确认后提交。

验收标准：
给出单元测试、接口测试、异常场景测试和一个 Playwright 端到端测试。
```

这才是 AI Coding 的好提示词。

## 9. 对视频生成来说，“讲故事”确实更有效，但生产级仍然需要结构化约束

Seedance 2.0 公开介绍里提到支持文字、图片、音频、视频多模态输入，并强调复杂交互、运动场景、物理准确度、可控性等能力。([中国科技网][3])

所以视频生成的提示词可以更偏故事，但如果是商业生产，仍然需要结构化：

```text
故事：
一位年轻工程师深夜调试系统，屏幕亮光映在脸上，最终系统恢复，窗外天色微亮。

风格：
写实、电影感、克制、科技企业宣传片风格。

角色：
30岁左右工程师，普通亚洲男性，穿深色卫衣。

镜头：
开场中景，随后推近到屏幕和眼神，最后拉远看到办公室。

限制：
不要夸张科幻，不要赛博朋克，不要出现错误文字。
```

所以视频是：

> **故事主导 + 镜头/风格/限制辅助。**

编程是：

> **业务目标主导 + 领域模型/接口/测试强约束。**

## 10. 我建议你逐个探讨的顺序

我们后面可以按这个顺序展开：

**第一，AI Coding 到底有没有新东西。**
重点讨论 Vibe Coding、Claude Code、Codex、Trae、扣子编程这些东西本质差异。

**第二，原型驱动开发到底适不适合 AI 时代。**
我倾向于结论是：适合做认知对齐，不适合做工程主线。

**第三，AI 时代更好的开发范式。**
我建议是：领域模型优先、契约优先、垂直切片、骨架驱动。

**第四，测试工程怎么设计。**
这可能是最关键的，可以单独展开成一套“AI Coding 测试体系设计”。

**第五，提示词到底写到什么程度。**
编程、视频、图片、Agent 工作流，应该采用不同提示词结构。
